# B 参与方确认：冻结版本只读复核与最小补丁建议

日期：2026-09-09。性质：实现审查建议；本文件不修改运行源码，不改变正在执行的 pilot，不代表补丁已经实现或经过真实模型验证。

## 决定

**当前实现对“共享任务清单、进度更新”已有对应，对“参与方确认”尚缺可审计的独立状态，应在本轮交付结束前补齐。** 不能把当前 pilot 宣称为已验证这个尚不存在的机制。可待当前冻结 pilot 完成并回收后，形成独立新版本，先通过离线验收，再由主负责人按已有授权和剩余预算决定是否执行短接入验证；无须为这个局部补丁重跑完整收费矩阵。

`work` 是自主选择的业务行动，可以作为“以履行行为接受任务”的理论替代，但当前代码没有保存接受责任的时点、参与人及未确认状态，无法区分“收到分派”“明确承诺”“实际执行”。用户已明确接受“参与方确认”，因此交付中不应事后把隐含执行解释为完整实现。显式、可选的 `confirm_joint_task` 是改动小且容易验收的修复。

## 最小补丁契约

1. **新增状态。** 每张原始工单初始化 `joint_participants=[]`、`joint_confirmed_by=[]`、`joint_activated_round=None`。申请联合流程成功时，将参与方设为已调查后可见的 `sorted(set([lead] + known_required))`，确认集合仍为空。错误首派后的协调主办也列入参与方，不把其错误身份当作实际维修资格。
2. **新增动作。** 在 `spec.py` 的 `ALLOWED_KINDS` 和 `ACTION_PARAM_KEYS` 增加 `confirm_joint_task`，参数为空字典；target是工单ID。本人身份只来自 `submit(actor_id, action)`，不得接受参数中的确认人、确认集合、资源或成功字段。
3. **准入与状态转移。** 只有已被提供并已申请联合流程的工单、尚未关闭、当前角色属于可见参与方且未确认，才能执行确认。确认只把绑定actor加入集合，写 `joint_task_confirmed` 事件。首次确认集合等于参与方集合时设置激活轮并写一次 `joint_coordination_activated` 事件。不能替其他人确认，不能把work自动算成确认，不能事后为已关闭工单补确认。
4. **提供与使用仍自愿。** 普通协调始终可用。联合申请后的未确认阶段，部门仍能依据现有合法分派完成日常任务；不增加work的“必须全部确认”门槛。以普通处理路径完成的问题仍能实质解决，不能因没有采用可选强化流程而失败。完整确认只激活正式联合板，不改变权限、任务需求、成本单价或物理工序。
5. **观察。** 联合申请后向被列入参与方的本人展示待确认分工、`joint_confirmed_by`、`joint_status=pending/active`；只向合法参与角色列出确认动作。未全确认时板标为“待确认提案”，保留普通反馈；全确认后再展示正式共享进度板。可见参与方来自已取得的调查信息，不能读取隐藏required/root作为新免费提示。C专项观察及协调规则不变。
6. **成本与排程。** 沿用所有非wait动作现有 `decision_cost`，确认占用本人本轮唯一动作机会；不另加资金、crew或新资源。已有联合板创建成本保留。work与implement的共同capital/crew竞争、角色轮转结算保持不变。确认可能增加时间和行政负担，实验不保证其有利。
7. **脚本正例。** 部门控制器在“协调申请”之后、“work”之前选择观察内的 `confirm_joint_task`；只能从 `available_actions` 取值。真实LLM仍可选择普通协作、等待或工作，不固定要求采纳。

“可选”指是否进入及明确采用联合流程由主体选择，不表示系统可以悄悄替主体补确认。也不应为了凸显B而删除普通协作，或给已确认工单添加时间折扣。

## 指标与验证器的最小兼容方式

保留现有 B 的 `eligible/offered/used/completed/objective_resolved` 字段及其数值口径，避免将当前运行结果重解释成另一种指标。`used`仍指联合流程申请，`completed`仍指申请后工单必要任务完成；在definition中写明二者都不证明全部参与方已确认。

新增 B 过程字段：

- `confirmed_participations`：不重复的工单×参与人成功确认数量。
- `fully_confirmed_cases`：发生全体确认激活事件的独立工单数。
- `full_confirmation_rate`：fully_confirmed_cases / used；分母为0记null。
- `confirmed_and_resolved`：已全体确认且实质解决的工单数。

上述变量用于记录机制过程，不直接解释为因果中介。`verify.py`须从成功确认动作与两个新事件独立重建集合，核对身份、成员、先后顺序、唯一激活和最终状态，再计算新增指标。不能把 `confirmed_participations` 放进“完成次数≤使用次数”的案件级链条，因为一个工单可以有多个参与人。应检查 `confirmed_and_resolved <= fully_confirmed_cases <= used <= offered <= eligible`。

## 必须通过的针对性验收

1. B=0普通协调仍可让独立任务同轮并行，误派仍可普通纠正；已有测试不改成弱对照。
2. B=1联合申请不会自动确认；两个参与人分别确认后只激活一次共享板。只有本人确认有效，非参与人和额外actor参数被拒绝。
3. 未确认/部分确认仍可按基准路径完成工单；解决不自动增加确认数，全体确认也不自动完成任何维修任务。
4. 重复submit维持当前同轮幂等；跨轮重复确认不得再次写成功事件或扩大集合，最多保留按现有规则计费的被拒绝尝试。
5. 确认只扣现有decision_cost、不耗capital/crew；不改变C规则和共同资源总量。确认状态及可选动作通过可见信息白名单测试。
6. JSON断点续跑和完整动作重放一致；独立验证器能检出篡改确认人、虚构激活以及缺失确认事件。
7. 八组合离线矩阵重新验证并保留新旧版本；脚本至少完成一个显式确认正例及既定结构项目，不预设B更好。短真实接入若没有选择确认动作，只能证明新增动作接口可见，不能声称该动作已实测成功。

## 版本与当前pilot边界

必须升业务规格版本并保存本次冻结源码及哈希。旧快照没有确认字段，禁止自动填入“已确认”；也不应把旧快照补空集合后冒充原字节重放通过。旧pilot由原版本和原哈希验证，新补丁用新目录、新manifest验证，不能覆盖仍在运行的文件。

`PolicyWorld`六个公开方法及Action外层结构均不变；router的typed接口无需改动，只需确认其角色提示没有独立固定动作枚举（若有则同步加入新动作）。当前router从观察传递available_actions，本身不需要新方法。若补丁实施，最小源码范围是 `spec.py`、`core.py`、`verify.py`、`tests/test_policy_core.py`，并按实际测试组织补对应验证器测试；本审查未修改这些文件。

本文件完成的是设计裁定与补丁建议，未执行源码修改、云端操作或收费调用。
